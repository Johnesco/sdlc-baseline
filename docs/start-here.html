The Solo Dev's Field Manual

You are one person. This is not bureaucracy — it is the memory, the brakes, and the second opinion you would otherwise have to be a team to get.

01Why bother, alone

Large teams adopt process to coordinate. You have nobody to coordinate with — so if you copy their reasons, you will correctly conclude you don't need any of it. The reasons for a solo developer are different, and they are real.

A process for one person buys three things a team gets for free. Memory: in nine months you will not remember why you rejected the obvious approach, and you will re-litigate it. Brakes: nobody is going to ask "have you actually decided this?" before you spend a weekend building it. A second opinion: you cannot review your own work with fresh eyes in the same hour you wrote it, and neither can an AI assistant.

The numbers below come from a real project of ours — a browser racing game, three months, shipped continuously. It had excellent commit hygiene and a strong decision record. It still lost real weeks to the two failure modes this standard is built to catch.

533
commits in 83 days
54
architecture decisions recorded
27
builds shipped, ~1 every 3 days
8
features built, then abandoned
6
traps walked into a second time

Those last two columns are the whole argument. Eight efforts reached working code before they reached a decision — free-direction driving, a rolling start, a ghost-race mode, a tutorial tab bar — and were then cut. Six times, a problem already written down was solved again from scratch, because the note existed but nobody read it before starting. Neither is a discipline problem. Both are missing steps.

02The loop

Every change — a feature, a bug fix, a refactor, a docs tweak — walks the same seven steps. Learn the shape once and you never have to decide what to do next.

Most changes compress. A one-line typo fix does not need a documentation review — but it still gets a ticket, and it still gets verified by a human who is not mid-flow. Compression is skipping the ceremony of a step, never the step itself. The full walkthrough, with examples, is in workflow.md.

03Three non-negotiables

Everything else in this standard is advice you can bend. These three are the ones that, when skipped, quietly cost you the weeks.

Rule 01

No code without a ticket

A GitHub Issue — or, for a decision, a six-line ADR stub. The ticket is not paperwork; it is the thing your commit message points at when you are trying to remember what you were doing and why.

Rule 02 · the newest, and the one that pays

Decide before you build

Anything above a tuning tweak gets a stub — Context and Decision, two paragraphs — before code. If you can't write the Decision paragraph, it isn't ready. That sentence is the whole mechanism. It is a sixty-second test that catches the eight-abandoned-features problem.

Rule 03

You cannot QA your own work — and neither can Claude

Whoever wrote it has blind spots about it, in exactly the places that matter. Verify is a separate act: step away, come back, use it like a stranger would. This is the one thing an AI assistant cannot do for you.

Rule 2 is new, and it is the reason this standard is worth re-reading if you last looked at it in June. See the six-line stub for the format and a worked example.

04Pick a profile

One question decides how much of this standard applies to you: do you operate a running service? Not "is it complicated" and not "am I alone" — do you have something that can be down at 3am.

core

You ship an artifact, or it runs on the user's machine. A browser game on itch.io, a desktop app, a CLI, a library, a static site with no backend.

  • The full loop, DoD, ADRs, versioning
  • Board, pull requests, milestones: optional
  • Your gate is one local test command
  • Your "production" is the file you uploaded

core+ops

You operate a service. A hosted site with a database and users, an API, a bot that has to stay up.

  • Everything in core, plus:
  • Deployment, environments, secrets
  • CI as the gate; branch protection
  • Incident response and rollback
Declare it once

Put **SDLC profile:** core under Working in this project in the project's CLAUDE.md. A project with no profile line is a core project — so if you do nothing, you get the smaller standard. Full detail in profiles.md.

The split is about what you operate, not how many people you are: a solo developer running a hosted site needs core+ops, and a whole team shipping a desktop app needs core. About a quarter of this standard sits behind that opt-in — if you are core, you never have to read it, and it never has to be true for you.

05Wearing every hat

This is the idea from large teams that transfers most directly, and it is the one that makes solo process work at all. On a team, five people hold five roles. Alone, you hold all five — but never two at once.

PO
Decides what gets built, and in what order. Says no. Accepts finished work. Always you, never delegated.
BA
Scopes it before anyone codes. Writes acceptance criteria, reads the docs for the affected area, spots where code and docs already disagree.
Dev
Writes the code. References the ticket, follows existing patterns. This is the hat an AI assistant wears best.
Documenter
Updates the docs in the same change. Bundled with Dev — not a follow-up task, and never a separate ticket.
QA
Tests it with fresh eyes. Always human, always separated in time from the writing. See rule 3.

Say the hat out loud when you switch — "wearing my PO hat, let's pick the next thing" — especially when working with Claude. It sounds silly and it works, because it stops you doing the thing every solo developer does: sliding from idea straight into code without passing through decide, then never testing it properly because you are still in build mode.

Full definitions, and what an AI can and cannot do in each role, are in roles.md.

06Your first week

Do not adopt all of this at once — that is the failure mode of every process rollout ever attempted. Adopt it in this order, and stop whenever it stops paying.

  1. Run the kickoff, once

    Paste the Quick Launch prompt from kickoff-checklist.md into a Claude Code session. It copies the vendored files, writes your CLAUDE.md, sets up labels, and asks you the handful of things it can't infer.

  2. Name your gate and your version

    One command that must pass before you tag a release — npm test, cargo test, whatever. And one file that holds the version number. Exactly one. Two places means one of them is already wrong.

  3. Walk the loop once, on something small

    Pick a change you'd normally just do. File the ticket anyway. Walk all seven steps. It will feel slow and slightly ridiculous. Do it once so the shape is in your hands.

  4. Write your first stub the moment you feel a decision

    The next time you catch yourself about to build something with a real choice inside it, stop and write six lines. This is the habit that pays for the whole standard.

  5. Cut a release and feel the gate hold

    Run the gate, tag the version, bump the build number, write the changelog entry for a human. Then you have walked the entire lifecycle once, and everything after is repetition.

Notice what is not on that list: a project board, pull requests, milestones, CI. None of them are step one. Several may never be worth it for you.

08What to skip

Permission, in writing, to not do things. A process you abandon in week three is worth less than a smaller one you keep.

ThingAdd it when
A project boardNever, probably. For one person gh issue list --state open is the board. Boards earn their keep by making work visible to other people.
Pull requestsSomeone else needs to review, or branch protection is doing real work. Otherwise commit to main with #XX: references.
MilestonesYou have enough issues that "what's in this release?" is genuinely unclear.
CIYou run a service, or you have ~10 tests and keep forgetting to run them. A local gate the release script enforces is enough for a long time.
A functional specThe project has enough features that you need one place that says what the behaviour is.
Coverage targetsYou have at least 20 tests. Before that it's aspirational fiction.

What you do not skip, at any size: the ticket, the decision, the human verify, and one gate before you ship.

09What makes this one ours

If you go and read a textbook SDLC, four things here will not be in it. They are the parts drawn from what actually happened to us, and they are the reason this is worth using instead of something off the shelf.

The decision gate sits where the cost changes

Textbook processes gate on quality — review, sign-off, approval, all after the work exists. This one gates on commitment, before it exists, because for a solo developer the expensive mistake is never bad code. It is good code for a feature you were always going to cut.

An ADR can be the ticket

Most standards make you file an issue and then, separately, document the decision. In core, for a decision, the six-line stub is the ticket — commits reference ADR-012: the same way they'd reference #42. One artifact, written before the work, completed after it.

The gate is local, and running it on request is legitimate

The industry answer is "CI runs everything on every push." For a project with no server, that is machinery guarding nothing. Here you name one command; it must pass before a release tag, and the release script refuses to cut a build without it. Whether it also runs on every commit is your business.

Versions describe what the player experiences

Semantic versioning encodes API compatibility, which is the right question only when your consumer is another program. Yours is a person. So MAJOR means they'd call it a different product, or their save files stopped loading; MINOR means new content; PATCH means fixes. Alongside it runs a build number that never resets — because when someone reports a bug, "build 36" identifies the exact file they were holding.

The one rule about this standard itself

Never paste these docs into a project. Link to them. A copy is a fork that nobody remembers making, and it will quietly disagree with the original within a month — see consumption.md. That is also why this page teaches shape and reasoning, and links out for every detail.
